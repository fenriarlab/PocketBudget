# PocketBudget 数据相容模型

> 状态：实施基线  
> 版本：1.0  
> 更新日期：2026-08-09

## 1. 目的

本文档定义 PocketBudget 中财务数据的统一语义、计算公式和一致性约束。后续数据库、Repository、页面展示、分析统计、备份恢复和测试均以本文档为准。

PocketBudget 是本地优先的个人预算工具，不是银行账户系统或完整会计软件。本模型追求的是预算领域内的严格相容，而不是在缺少账户余额、期初资产和负债数据时推导虚假的净资产。

## 2. 设计原则

1. **事实唯一**：一项业务事实只保存在一个权威位置。
2. **派生一致**：页面不自行发明公式，统一从领域计算层读取派生指标。
3. **名称精确**：消费、存钱、预算占用、结余和余额不得混用。
4. **月份统一**：同一页面中的摘要、日历、预算和分析必须使用同一个月份上下文。
5. **历史稳定**：归档目标不得改变历史月份的收支与预算结果。
6. **可校验**：关键相容关系必须能由自动化测试和数据诊断验证。

## 3. 数据分类

### 3.1 原始事实

原始事实由用户行为产生，是计算其他指标的权威来源。

| 事实 | 含义 | 当前存储 |
| --- | --- | --- |
| 收入交易 | 外部资金流入 | `transactions`，`type = INCOME` |
| 消费交易 | 购买商品或服务造成的资金流出 | `transactions`，`type = EXPENSE`，不含存钱划拨 |
| 存钱流水 | 向目标存入或从目标提取 | `savings_logs`，存入为正、提取为负 |
| 月度预算 | 某个月允许使用的预算上限 | `budgets` |
| 存钱目标 | 目标名称、目标金额、目标日期和状态 | `savings_goals` |
| 预算分配 | 某笔正数存钱是否占用当月预算 | 短期由 `savings_logs.deduct_from_budget` 表达 |

### 3.2 计划值

计划值表达用户意图，不代表已经发生的资金事实：

- 月度预算上限
- 存钱目标金额
- 存钱目标日期

### 3.3 派生值

下列数据必须由原始事实计算，不得由页面各自维护：

- 月收入
- 月消费
- 月净存钱
- 预算已用
- 剩余预算
- 月收支结余
- 月可分配结余
- 目标已存、剩余金额和完成进度
- 每日建议消费上限
- 日历消费压力

`savings_goals.current_amount` 在过渡期内可作为缓存保留，但不是真相来源，必须始终能够从 `savings_logs` 重建。

## 4. 统一术语与公式

设月份为 $p$，存钱目标为 $g$。

### 4.1 月收入

$$
I_p = \sum \text{当月收入交易金额}
$$

收入金额必须大于 0。内部存钱提取不属于收入。

### 4.2 月消费

$$
C_p = \sum \text{当月消费交易金额}
$$

月消费只包含真实消费。存钱是内部资金划拨，不进入月消费和消费分类分析。

### 4.3 月净存钱

$$
S_p = \sum \text{当月存钱流水金额}
$$

存入为正，提取为负。例如当月存入 1000、提取 200，则月净存钱为 800。

### 4.4 计入预算的存钱

$$
A_p = \sum \text{当月标记为计入预算的正数存钱流水}
$$

只有用户明确选择“计入本月预算”时，该笔存钱才进入 $A_p$。提取默认不返还预算额度，避免通过提取目标资金人为扩大消费预算；删除或编辑原存钱流水时，预算占用随原流水同步修正。

### 4.5 预算已用与剩余预算

$$
U_p = C_p + A_p
$$

$$
R_p = B_p - U_p
$$

其中：

- $B_p$：月度预算
- $U_p$：预算已用
- $R_p$：剩余预算

预算未设置时，$B_p$ 必须为 `null`，UI 显示“未设置预算”。不得使用 5000 或其他隐式默认值参与计算。

### 4.6 月收支结余

$$
F_p = I_p - C_p
$$

该指标回答“本月收入扣除真实消费后还剩多少”。存钱是内部划拨，因此不从月收支结余中重复扣除。

### 4.7 月可分配结余

$$
D_p = I_p - C_p - S_p
$$

该指标回答“考虑本月存入和提取后，仍未分配给消费或目标的金额是多少”。它是月度流量指标，不是银行账户余额。

### 4.8 目标已存与进度

$$
Saved_g = \sum \text{目标 } g \text{ 的全部存钱流水}
$$

$$
Remaining_g = \max(0, Target_g - Saved_g)
$$

$$
Progress_g = \min\left(1, \frac{Saved_g}{Target_g}\right)
$$

目标余额不得小于 0。允许超过目标金额，但展示进度最多为 100%。

### 4.9 每日建议消费上限

仅对当前月计算动态建议：

$$
DailyAllowance_p = \frac{\max(0, R_p)}{\text{当月剩余天数（含当天）}}
$$

历史月份和未来月份不展示“剩余天数消费建议”。历史月份可展示实际日均消费，未来月份可展示计划日均预算，但必须使用不同名称。

### 4.10 日历消费压力

日历压力只基于真实消费，不把收入或存钱划拨计入消费压力。

$$
DailyBaseline_p = \frac{B_p - A_p}{\text{月份总天数}}
$$

$$
Pressure_d = \frac{Consumption_d}{DailyBaseline_p}
$$

若预算未设置或可消费基准小于等于 0，则压力状态为“不可评估”，不得默认为最高压力。

## 5. 不支持的指标

当前数据模型没有账户、期初余额和负债，因此不能可靠计算以下指标：

- 总资产
- 净资产
- 银行余额
- 现金余额
- 流动资产

在账户模型落地前，UI 不得使用上述名称。首页可分别展示“本月可分配结余”和“目标累计已存”，但不得将二者相加后称为“总资产”。

## 6. 领域快照

后续实现统一的 `MonthlyFinancialSnapshot`，作为首页、计划页、分析页和日历的月度指标来源。

建议字段：

```dart
class MonthlyFinancialSnapshot {
  final String period;
  final double income;
  final double consumption;
  final double netSavings;
  final double budgetedSavings;
  final double? budget;
  final double? budgetUsed;
  final double? remainingBudget;
  final double cashflowSurplus;
  final double distributableSurplus;
  final double? dailyAllowance;
}
```

金额字段名称必须表达业务含义。禁止继续使用含义不清的 `monthlyExpense`、`balance`、`totalAssets` 在页面间传递不同口径的数据。

## 7. 数据不变量

以下规则必须由 Repository、迁移、备份恢复和测试共同保障：

| 编号 | 不变量 |
| --- | --- |
| INV-01 | 收入和消费交易金额必须大于 0 |
| INV-02 | 存钱流水金额不能为 0 |
| INV-03 | 任一目标的流水总和不得小于 0 |
| INV-04 | 目标已存必须等于该目标全部流水之和 |
| INV-05 | 计入预算的记录必须是正数存钱流水 |
| INV-06 | 一笔预算分配只能关联一笔存钱流水 |
| INV-07 | 存钱划拨不得进入消费分类统计 |
| INV-08 | 页面所有月度数据必须使用同一个 `period` |
| INV-09 | 未设置预算与预算为 0 是两个不同状态 |
| INV-10 | 备份恢复后必须重新计算缓存并验证全部关联 |
| INV-11 | 归档目标不得删除或改写历史流水 |
| INV-12 | 所有跨表写入必须在同一个 SQLite 事务中完成 |

## 8. 页面展示契约

| 页面 | 应展示 | 禁止混入 |
| --- | --- | --- |
| 首页摘要 | 月消费、月收入、月收支结余 | 存钱划拨不得计入月消费 |
| 首页建议 | 当前月剩余预算、每日建议消费 | 历史月份不得套用当前日期 |
| 日历 | 每日真实消费与压力 | 收入、存钱划拨不得影响压力 |
| 计划页预算 | 预算、预算已用、剩余预算 | “已使用”必须包含用户选择计入预算的存钱 |
| 存钱目标 | 目标已存、目标金额、剩余金额、目标日期 | 不得使用缓存值覆盖流水事实 |
| 分析页 | 所选月份的消费分类 | 不得统计全部月份或存钱划拨 |

推荐文案替换：

| 旧名称 | 统一名称 |
| --- | --- |
| 月支出 | 本月消费 |
| 存钱支出 | 存钱分配 |
| 已使用 | 预算已用 |
| 结余 | 本月收支结余 |
| 流动余额 | 本月可分配结余 |
| 总资产 | 暂不展示 |

## 9. 生命周期规则

### 9.1 存钱目标

- 活跃目标允许存入、提取、编辑计划信息和归档。
- 已完成目标仍保留流水，可继续展示或归档。
- 已有流水的目标默认只能归档，不能物理删除。
- 物理删除仅用于没有流水的空目标，或明确的数据清理流程。

### 9.2 历史月份

- 历史事实应保持稳定。
- 编辑或删除历史记录属于显式修正，必须同步重算对应月份快照。
- 归档目标不得删除关联的历史消费、预算分配或存钱流水。

### 9.3 金额

当前模型使用 `double`。后续数据库迁移应评估改用整数分存储，避免浮点累计误差。在完成迁移前，比较金额时必须使用统一精度策略，不直接依赖浮点完全相等。

## 10. 备份与恢复

备份必须包含原始事实和计划值。派生值可导出用于兼容，但恢复后不得直接信任。

恢复顺序：

1. 校验备份格式和版本。
2. 在单个事务内恢复事实表。
3. 重建存钱与预算关联。
4. 从 `savings_logs` 重算所有目标余额缓存。
5. 执行 INV-01 至 INV-12 校验。
6. 校验失败则回滚整个恢复事务。

## 11. 渐进实施路线

### Phase 1：统一计算入口

- 新增 `MonthlyFinancialSnapshot` 和领域计算服务。
- 所有页面使用同一月份参数和同一快照。
- 增加公式和不变量的纯 Dart 单元测试。

### Phase 2：修正展示口径

- 将月支出拆分为“本月消费”和“预算已用”。
- 从消费分类中排除存钱划拨。
- 移除“总资产”和“流动余额”的不准确命名。
- 明确预算未设置状态。

### Phase 3：强化存钱一致性

- 所有目标余额从流水重算。
- 数据层拒绝导致目标余额为负的操作。
- 将目标删除改为归档。
- 备份恢复后强制执行一致性校验。

### Phase 4：迁移预算分配

- 停止用普通 `EXPENSE` 交易模拟存钱占用预算。
- 引入显式预算分配字段或独立关联表。
- 迁移现有 `tx_savings_<logId>` 数据并保持历史结果不变。

### Phase 5：金额与账户扩展评估

- 评估金额改为整数分。
- 仅在产品确认需要账户余额和净资产时，引入账户与转账模型。

## 12. 验收标准

数据相容模型完成实施时，应满足：

- 给定同一组事实数据，首页、计划页和分析页对同一指标得出完全一致的结果。
- 切换月份后，摘要、预算、日历和分析同时切换。
- 存入目标可占用预算，但不会成为消费。
- 提取目标会降低目标已存，但默认不增加消费预算。
- 任意新增、编辑、删除、恢复操作后，目标余额等于流水总和。
- 归档目标不会改变任何历史月份数据。
- 未设置预算时不展示伪造的预算金额或压力等级。
- 应用不再展示无法由现有事实推导的“总资产”。
